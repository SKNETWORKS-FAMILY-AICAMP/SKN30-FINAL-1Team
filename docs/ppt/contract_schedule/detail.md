# 계약·일정 에이전트 상세 근거

이 문서는 발표에서 "현재 구현"이라고 말해도 되는 범위를 적는다.
4장 이후의 브리핑 RAG·자동 갱신은 `jiyu-park/briefing-document-rag` 브랜치에 있고
develop 에는 아직 병합되지 않았다. 병합 전에 발표한다면 그 사실을 함께 말한다.

## 1. 에이전트별 역할

| 항목 | 계약관리 | 일정관리 |
| --- | --- | --- |
| 목적 | 다음 미팅 필요성과 이유를 설명하고 미팅 준비용 브리핑 제공 | 조건에 맞는 일정 후보 제공 |
| 핵심 입력 | 회사·딜 현황, 위험 신호, 최근 확정 보고서 / 브리핑에는 일정·RAG 문맥 추가 | 딜, 탐색 기간, 소요 시간, 이유, 담당자의 기존 활동 시간 |
| 핵심 출력 | risks, missing_information, recommended_actions, next_meeting_suggestion / 브리핑에는 contract_summary, source_refs | schedule_candidates, conflicts |
| LLM 역할 | 입력 근거를 바탕으로 설명·행동·미팅 조건 생성 | 후보 시간·제목·이유·우선순위 생성 |
| 실제 업무 변경 | 추천 생성만으로 계약·딜을 수정하지 않음 | 후보 생성만으로 일정을 등록하지 않음 |

## 2. 자동 추천 실행 흐름

1. 업무 API가 데이터 저장을 마친 뒤 `queue()`를 호출한다.
2. FastAPI BackgroundTasks가 `_run_pipeline()`을 실행한다.
3. LLM 설정·진행 중 실행·최근 실행 등을 확인하고 해당 딜의 입력을 준비한다.
4. 계약 실행을 AgentRun에 등록하고 공통 실행 경로로 실행한다.
5. 미팅 제안이 있으면 그 조건과 담당자의 기존 일정으로 일정 실행을 만든다.
6. 서버 후처리를 통과한 후보가 있으면 추천 테이블에 저장한다.
7. 캘린더는 저장된 추천을 조회한다.
8. 사용자가 후보를 선택해 일정 등록을 요청한다.
9. API가 추천을 선점하고 일정을 저장한 뒤 브리핑 생성을 요청한다.

브리핑은 이 경로에서만 만들어지지 않는다. 자료·미팅·딜이 바뀔 때마다 서버가 미리
다시 만들어 둔다 — 4장 "브리핑 생성 시점" 참고.

시작 지점: 보고서 확정, 영업 건 생성, 단계 이동, 딜에 연결된 일정 수동 등록,
CS 상태를 in_progress로 설정하는 처리.
동일 딜의 queued/running 실행과 최근 실행을 검사하며 쿨다운은 코드상 10분이다.
항상 후보가 나온다고 보장하지 않는다. 미팅 제안 없음·후보 없음·실행 실패면 추천 저장 없이 끝날 수 있다.

공통 실행은 `agent_runs.execute()`를 통해 worker의 선점·실행 규칙을 사용한다.
별도 worker의 큐 폴링 경로도 존재한다. 따라서 모든 추천을 별도 컨테이너 worker만 처리한다고
단정하지 않는다. 파이프라인 순서 결정은 서버 코드가 맡는다.

## 3. 판단과 검증의 구체 내용

### 계약 위험

서버가 계약 만료, 견적 만료, 납기 경과, 장기 미접촉, 미해결 CS, 계약 정보 누락,
계약 후 재방문 시점 같은 신호를 계산한다.
예: 계약 종료 30일 이내, 견적 유효기한 14일 이내, 미접촉 30일 이상을 확인한다.
이것은 현재 규칙값이며 법적·업계 표준이라는 뜻이 아니다.
프롬프트는 입력에 없는 위험·약속·계약 조건을 새로 만들지 않도록 지시한다.
Pydantic이 필드·열거형·길이 등을 검사하지만 모든 의미적 정확성을 증명하지는 않는다.

### 일정 검증

현재 코드는 Asia/Seoul 평일 09:00~18:00, 과거 후보 제외, 기존 활동과 겹침 제거,
요청 소요 시간에 맞춘 길이 보정 후 재검사, 선호 날짜 범위 확인, 후보 중복 제거를 수행한다.
사용자에게 보여줄 후보는 최대 5개다. 보정 후 모든 후보가 탈락할 수 있다.
현재 선호 기간 보정·업무시간 정책을 최종 제품 정책으로 확정했다는 의미는 아니다.

### 사용자 승인 경계

추천 선점과 일정 등록을 같은 트랜잭션에서 처리해 같은 추천의 중복 등록을 방어한다.
시간 충돌은 후보 생성 때 필터링하고, 일정 등록 후 최신 일정을 다시 조회해 경고한다.
“승인 시 충돌을 검사해 등록 자체를 차단한다”라고 발표하면 현재 코드와 다르다.
브리핑 큐 등록 실패는 이미 저장된 일정을 되돌리지 않고 경고로 전달한다.

## 4. 브리핑 RAG의 실제 구현

### 검색어

`고객사명 + 일정 제목 + 이 일정에 연결된 딜의 제목 + 일정 메모`를 문자열로 조합한다.
이 미팅이 다루는 상품이 있으면 앞 350자를 남기고 그 상품명들을 덧붙인다.
최종 길이는 500자로 자른다. 별도 LLM이 검색어를 생성하는 구조가 아니다.

이전 구현은 그 고객사의 열린 딜 제목을 모두 넣었다. 지금은 이 일정의 딜만 넣는다.

### 검색 범위

- 팀 범위, 삭제되지 않은 문서, 처리 완료 파일을 확인한다.
- 문서별 최신 처리 완료 파일을 기준으로 청크를 조회한다.
- 자료실의 등록자 공개 범위를 검색에도 적용한다. 팀원은 본인이 올린 자료와 팀장이
  올린 자료만 근거로 받는다. 다른 팀원의 비공개 자료는 검색되지 않는다.
- 딜·고객사·상품 연결 조건을 OR로 사용한다.
- 고객사 범위에는 그 고객사의 다른 딜에 연결된 자료도 들어갈 수 있다.
- 상품 조건은 딜 대표 상품과 견적 품목에서 모은다. 일정에만 지정된 상품은 넣지 않는다.

### 검색 방법

`document_chunk.embedding_vector`는 pgvector 컬럼이며 384/1536 차원에 각각 HNSW 부분
인덱스를 둔다. 이전 JSONB `embedding` 컬럼은 롤백용으로 남아 있고 검색에 쓰지 않는다.

- 키워드 점수는 PostgreSQL에서 계산한다. 청크 본문을 토큰 배열로 나눠 질의 토큰의
  적중 비율을 매긴다. 팀 전체 청크를 파이썬으로 끌어와 채점하던 경로는 없어졌다.
- 벡터 검색은 코사인 거리를 쓰고, 설정 차원과 저장된 임베딩 모델 식별자가 같은 청크만
  본다. 다른 모델로 만든 벡터는 섞지 않는다. 유사도 하한은 설정값이며 기본 0.45다.
- 두 결과는 Reciprocal Rank Fusion(`1/(60+순위)`)으로 합친다. 코사인 점수와 키워드
  비율을 직접 비교하지 않기 위해서다. 각 경로의 후보는 `max(20, 요청수×4)`개로 자른다.
- 임베딩이 설정되지 않았거나 질의 임베딩에 실패하면 키워드 결과만 쓴다.

상위 5개 청크를 선택한다. 문서 5개가 아니라 청크 5개다.
선택 청크와 해당 파일의 저장 요약을 묶어 최대 12,000자 문맥 블록으로 전달한다.
실행 결과에 검색 방식(`hybrid`/`keyword`/`none`)과 상태를 함께 남겨 화면이 구분해 쓴다.
현재 운영 환경에서 임베딩이 활성화됐는지는 확인하지 않았다.

### 제품 자료는 RAG가 아니다

딜 대표 상품과 견적 품목에 연결된 자료는 검색하지 않고 연결 관계로 바로 조회한다.
검색 점수도 상위 5개 제한도 적용하지 않는다.
이 목록은 관련 자료와 같은 실행 스냅샷에 `product_documents`로 함께 저장한다.

### 생성과 출처

등록 일정·영업현황·위험 신호와 검색 문맥을 브리핑 생성에 전달한다.
문서 내용은 외부 자료임을 구분한 프롬프트 블록으로 넣는다.
조회하지 않은 문서 ID를 최상위 source_refs에 반환하면 제거한다.
검색 실패 시 빈 문맥으로 진행할 수 있으며, 근거가 없으면 missing_information에 남기도록 지시한다.
문서 ID 검증은 문장 단위 사실 검증이나 출처의 의미적 일치 보장이 아니다.

### 브리핑 생성 시점

**화면은 브리핑을 만들지 않는다.** 미팅 상세는 저장된 결과를 조회만 한다.
이전 구현은 브리핑이 없으면 상세 화면이 생성을 요청하고 완료까지 폴링했다. 지금은
그 POST 경로가 없다. 임시로 두었던 `브리핑 새로고침` 버튼도 제거했다.

서버가 미리 만들어 둔다. 예약 시점은 다음과 같다.

| 트리거 | 대상 |
| --- | --- |
| 미팅 등록 | 그 미팅 |
| 미팅의 담당자·고객사·딜·상품·시작 시각 변경 | 그 미팅 |
| 자료 처리 완료, 자료요약 승인 | 그 자료가 걸린 범위의 미래 미팅 |
| 자료 삭제, 자료의 딜·고객사·상품 연결 변경 | 변경 전 범위와 변경 후 범위 양쪽 |
| 딜의 대표 상품·견적 품목·고객사 변경 | 그 딜의 미래 미팅 |

- 지금 이후에 시작하고 완료되지 않은 미팅만 예약한다. 지난 미팅은 다시 만들지 않는다.
- 자료가 딜에만 걸려 있으면 그 딜의 미팅만 본다. 같은 고객사의 다른 딜은 건드리지 않는다.
- 한 번의 트리거로 예약하는 미팅은 최대 50건이며 가까운 미팅부터 채운다.
- 자료 처리가 **커밋된 뒤에만** 예약한다. 그 전에 예약하면 아직 저장 중인 청크가
  검색될 수 있다. 처리에 실패한 자료는 아무것도 예약하지 않는다.
- 예약은 큐에 행을 넣을 뿐이다. 자료 저장 API 요청이 LLM 완료를 기다리지 않는다.

### 중복과 경합 처리

실행 요청의 멱등키를 `미팅 ID + source revision`으로 만든다.
source revision은 "검색용 버전" 같은 증가 숫자가 아니라 **검색 대상 상태의 sha256 지문**이다.
입력은 미팅의 검색 범위(고객사·딜·담당자·상품·시작 시각), 딜의 상품 집합, 그리고 그 범위에서
실제로 읽히게 될 문서·파일의 `(document_id, file_id, version_no, processed_at)` 목록이다.
파일 목록은 검색과 같은 조건으로 뽑으므로 삭제·연결 변경·재업로드·재처리가 전부 지문을 바꾼다.

- `agent_run`의 기존 `UNIQUE (requested_by_member_id, idempotency_key)`가 중복을 결정한다.
  메모리 debounce가 아니라서 프로세스를 다시 띄워도, worker가 여럿이어도 같은 상태의
  브리핑은 한 번만 만들어진다.
- 키가 "실행 중 여부"가 아니라 "자료 상태"에 묶여 있어, 이미 도는 실행이 있어도 자료가
  바뀌면 새 요청이 들어간다. 실행 시작 뒤에 올라온 자료를 버리지 않는다.
- 실행이 끝나면 지문을 다시 계산해 비교한다. 그 사이에 자료가 또 바뀌었으면 후속 실행을
  예약한다.
- 화면에 세울 브리핑은 "가장 최근에 끝난 실행"이 아니라 **가장 나중 상태의 자료를 보고
  만든 성공 실행**을 고른다. 옛 자료로 시작한 실행이 늦게 끝나도 더 새 자료로 만든
  브리핑을 덮지 못한다.
- 후보는 성공한 실행뿐이다. 갱신이 실패해도 마지막 성공 브리핑은 그대로 남고 실패는
  따로만 알린다.

새 테이블도 새 컬럼도 만들지 않았다. 기존 `agent_run`의 멱등키·`request_hash`·`source_refs`와
기존 worker 컨테이너를 그대로 쓴다. 이 기능 때문에 필요한 마이그레이션은 없다.
다만 pgvector 검색은 `20260912_0031_document_vectors.sql` 적용이 선행되어야 한다.

### 화면 동작

- 상세 진입 시 GET 한 번으로 저장된 최신 성공 브리핑을 즉시 표시한다.
- 갱신이 도는 중이면 제목 옆에 `최신 자료 반영 중`만 작게 붙이고 본문은 가리지 않는다.
  그 상태일 때만 5초 간격 GET으로 결과를 교체하며, 이 폴링은 실행을 만들지 않는다.
- 결과가 한 번도 없을 때만 `AI 브리핑 준비 중`을 보여준다.
- 갱신 실패는 한 줄 안내로만 알리고 이전 브리핑을 그대로 둔다.

## 5. 제품 자료와 관련 자료

두 목록은 브리핑 본문과 **같은 실행 스냅샷**에 저장된다. 본문·제품 자료·관련 자료가
한 결과로 함께 교체되므로, 화면에 보이는 근거와 본문이 만들어진 시점이 어긋나지 않는다.

| 구분 | 📦 제품 자료 | 📎 관련 자료 |
| --- | --- | --- |
| 범위 | 딜 대표 상품 · 견적 품목 | 딜 · 고객사 · 해당 고객사의 딜 · 상품 |
| 방식 | 연결 관계 조회 | 키워드 + pgvector 하이브리드 검색 |
| 개수 | 제한 없음 | 상위 5청크 |
| 표시 | 파일명 · 저장 요약 | `RAG 검색` 태그 · 페이지 · 발췌 |
| 저장 | 실행 입력 스냅샷 | 실행 입력 스냅샷 |

이전에는 관련자료를 `GET /activities/{id}/documents`로 따로 조회했다. 그 엔드포인트와
프런트엔드 훅은 제거했다. "관련자료는 브리핑과 무관한 별도 조회"라고 발표하면 현재 코드와 다르다.

조회 시점에 팀·삭제 여부·등록자 공개 범위를 **다시** 검사한다. 브리핑을 만든 뒤에 지워졌거나
권한이 바뀐 자료는 저장된 근거에 남아 있어도 화면에 나오지 않는다.

제품 자료가 화면에 보여도 브리핑 본문이 그 자료를 인용했다는 뜻은 아니다.
인용 여부는 줄에 붙는 `브리핑에 인용됨` 표시로만 구분한다.

## 6. 기술 선택과 공통 시스템의 관계

| 기술·요소 | 이 기능에서의 실제 용도 |
| --- | --- |
| FastAPI BackgroundTasks | 업무 저장 뒤 계약·일정 파이프라인 시작, 브리핑 갱신 예약 |
| Python 서비스 파이프라인 | 계약 결과를 일정 입력으로 전달 |
| Pydantic / JSON Schema | LLM 입력 허용 목록과 출력 형태 검증 |
| httpx / OpenAI 호환 API | generate_structured()가 모델 요청 수행 |
| PostgreSQL / SQLAlchemy | 영업 데이터·실행 기록·추천·문서 청크 조회와 저장 |
| pgvector | 문서 청크 임베딩 저장과 코사인 검색, 차원별 HNSW 인덱스 |
| AgentRun / worker | 작업 선점, 상태·결과, 오류·재시도, 토큰 사용량 관리, 브리핑 갱신 큐 |
| React / TypeScript | 추천 조회·선택과 상세 브리핑 조회 (생성 요청 없음) |
| RAG 검색 서비스 | 자료실 처리 결과를 브리핑 문맥으로 제공 |

프로젝트 전체는 LangChain을 사용하지만 이 계약·일정 호출은 generate_structured()의 HTTP 경로다.
LangGraph, DeepAgents 자율 위임을 이 기능의 구현으로 표시하지 않는다.
벡터 검색은 전용 검색 엔진이 아니라 PostgreSQL 확장(pgvector)이다.
현재 LLM 모델·임베딩 모델명은 설정에 따라 달라지므로 발표 전 운영값 확인이 필요하다.

## 8. 데모 시나리오와 준비할 화면

합성 데이터 예시이며 실제 고객 정보나 실행 결과가 아니다.

1. 가상 고객사와 담당자, 견적 기한이 가까운 영업 건, 확정 보고서를 준비한다.
2. 담당자의 기존 일정 일부를 채우고 업무 이벤트를 발생시킨다.
3. 캘린더에서 생성된 추천 이유·후보를 확인한다. 후보가 없으면 실행 상태와 입력을 확인한다.
4. 후보를 선택해 일정 등록을 확인한다.
5. 미팅 상세를 열어 첫 브리핑과 제품 자료·관련 자료를 확인한다.
6. 같은 딜에 가상 자료를 새로 올려 처리 완료까지 기다린다. 업로드 요청은 바로 끝나고
   브리핑 생성은 뒤에서 돈다.
7. 미팅 상세를 다시 연다. 이전 브리핑이 그대로 보이고 제목 옆에 `최신 자료 반영 중`이
   붙었다가, 갱신이 끝나면 본문·제품 자료·관련 자료가 한 번에 바뀌는 것을 보인다.
8. 다른 담당자가 올린 비공개 자료와 다른 고객사 자료가 근거에 섞이지 않았는지 확인한다.

필요한 캡처: 가상 영업현황 / 추천 카드 / 등록 일정과 브리핑 / 갱신 중 상태 / 교체된 근거.
운영 모델명·실제 생성 결과·실패 케이스·자료 처리 완료 여부를 발표 전에 확인한다.

데모에서 갱신이 보이려면 worker 컨테이너가 떠 있어야 한다. 예약은 DB 큐에 쌓일 뿐이고
실행은 worker가 한다. 배포 스크립트는 이미 그 컨테이너를 띄우지만 로컬 시연에서는
`python -m app.services.agent_worker`를 따로 실행한다.

## 9. 평가 계획과 확인된 검증의 차이

이전 폴더 이관에서 관련 테스트 167개 통과, 외부 연동 5개 제외를 확인했다.

브리핑 자동 갱신 작업에서는 `jiyu-park/briefing-document-rag` 기준으로 백엔드 전체
1,467개 통과(10개 건너뜀), 프런트엔드 115개 통과, 빌드·린트·포맷 통과를 확인했다.
갱신 경로 전용 테스트 32개가 여기 포함된다 — 미래 미팅만 예약, 무관한 딜·지난 미팅
제외, 처리 실패 시 예약 없음, 같은 revision 중복 방지, 늦게 끝난 옛 실행의 덮어쓰기
방지, 후속 예약, 실패 시 이전 성공 유지, 삭제·연결 변경 재생성, 권한·팀 범위 제외.
합성 API 응답으로 실제 미팅 상세를 브라우저에 렌더링해 새로고침 버튼 제거와 상태
전환도 확인했다.

이 수치는 코드 회귀 검사이며 AI 품질 점수·속도·운영 성능이 아니다.
실제 DB를 쓰는 pgvector 통합 테스트는 전용 로컬 DB가 있어야 하며 이번에 실행하지 않았다.

발표 전 별도 평가표를 채운다.

| 평가 항목 | 방법 | 현재 결과 |
| --- | --- | --- |
| 사실·대상 정확성 | 가상 딜과 정답 근거를 대조해 없는 조건·다른 딜 혼입 확인 | 미측정 |
| 미팅 유용성 | 목표·질문·준비 행동의 구체성을 사람이 평가 | 미측정 |
| 일정 조건 준수 | 과거·업무시간·겹침·기간·소요 시간 조건별 후보 검사 | 실출력 평가 미측정 |
| 출처 정확성 | 조회된 문서 ID와 주장 근거를 각각 확인 | 실출력 평가 미측정 |
| 갱신 적시성 | 자료 처리 완료부터 새 브리핑 게시까지의 지연 측정 | 미측정 |
| 장애·빈 결과 | 자료 없음·검색 실패·후보 없음·중복 승인 시나리오 | 코드 검증 완료, 실환경 데모 검증 필요 |
| 시간·비용 | 단계별 지연과 토큰 사용량 기록 | 미측정 |

없는 계약 조건 생성, 다른 딜 정보 혼합, 근거와 다른 출처는 중대 오류로 분류하는 것을 제안한다.
구체적인 합격 기준과 평가 표본 수는 팀 합의가 필요하다.
