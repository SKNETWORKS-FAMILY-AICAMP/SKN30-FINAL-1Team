## 1. 전처리 개요

- **전처리 목적**
  - 실제 고객사·거래처·제품 정보가 담긴 원본 영업 자료를 서비스 개발·데모에 안전하게 쓸 수 있도록 비식별화(가명처리)한다.
  - 미팅 분석 Agent가 산출하는 딜 승산 점수(0~100)를 학습시키기 위해 외부 공개 B2B 영업 데이터(Salvirt)를 정제한다.
- **전처리 범위**
  - 정형 데이터: 매출·발주·가격표 등 XLS/XLSX (`data/sample/`)
  - 비정형 문서: 사업자등록증·인허가증·결제내역 등 DOCX/PDF (`data/sanitized_docs/`)
  - 외부 학습 데이터: Hugging Face `markobo/B2B_Sales_data` CSV (448행 23컬럼)
- **사용 도구**: openpyxl/pandas(표 변형·검증), python-docx(문서 변형), Python 표준 정규식(값 판정), scikit-learn(`OneHotEncoder`, `LogisticRegression`, `StratifiedGroupKFold`)

| 금액 | 상한금액, 정액수가, 계약·매출 금액 | 실제 금액 열 여부 | 원본 대비 ±5~10% 범위로 일괄 조정(0·빈 셀 유지, 합계·수량×단가 관계 유지) |

### 2.2 품질 이슈 진단 및 자동 검증

**① 비식별화 트랙**

| 처리 단계 | 입력 | 출력 | 목적 |
| --- | --- | --- | --- |
| 식별값 판정 | 원본 표/문서 | 회사·제품·개인정보·금액·날짜 열 분류 | 변경 대상과 유지 대상 구분 |
| 가상값 매핑 | 판정된 식별값 | 회사/제품별 1:1 가상값 | 동일 대상 일관성 확보(중복 매핑·병합 금지) |
| 금액·날짜 변형 | 원본 금액/날짜 | ±5~10% 조정, 7~30일 이동 | 실제 값 은닉, 통계적 패턴은 보존 |
| 구조 보존 검증 | 원본/변형본 XLSX·DOCX | 시트 수·순서·병합·서식·수식 비교 결과 | 문서 손상·구조 훼손 방지 |
| 잔존 식별정보 전수 검색 | 변형본 | 원본 회사명·개인정보 잔존 여부 | 비식별화 누락 방지 |

**② 학습 데이터 트랙**

| 처리 단계 | 입력 | 출력 | 목적 |
| --- | --- | --- | --- |
| 정제 | 원본 448행 23컬럼 | 공백 제거, `Status`→`Won`=1/`Lost`=0 | 형식 통일 |
| 중복 제거 | 정제 데이터 | 365행 | 학습 편향 방지 |
| 특성 선택 | 22개 범주형 특성 | 10개 특성(`Authority`, `Competitors`, `Purch_dept`, `Budgt_alloc`, `Forml_tend`, `RFI`, `RFP`, `Posit_statm`, `Scope`, `Needs_def`) | 단일 미팅에서 명확히 추출 가능한 특성만 사용 |
| 인코딩 | 10개 범주형 특성 | One-Hot 벡터(`handle_unknown="ignore"`) | `Unknown`을 유효 범주로 유지하면서 학습 가능한 형태로 변환 |
| 그룹 지정 | 인코딩된 365행 | 133개 고유 특성 조합 그룹 | 동일 조합이 학습/평가에 겹치지 않도록 분리 |

### 2.3 전처리 파이프라인 흐름도

```
[비식별화 트랙]
data/raw/ (원본, Git 미포함)
  → 식별값 판정(회사/제품/개인정보/금액/날짜)
  → 가상값 매핑(회사·제품 1:1, 파일 간 일관성 유지)
  → 금액 ±5~10% 조정 / 날짜 7~30일 이동
  → 구조 보존 검증(시트·서식·수식) + 잔존 식별정보 전수 검색
  → data/sample/(표), data/sanitized_docs/(문서)

[학습 데이터 트랙]
B2B_Sales_data.csv (448행 23컬럼)
  → 공백 정리, Status → Won/Lost 이진화
  → 완전 중복 제거(83건) → 365행
  → 10개 입력 특성 선택
  → One-Hot Encoding(handle_unknown="ignore")
  → 133개 고유 조합 그룹 지정
  → StratifiedGroupKFold 학습/검증
  → LogisticRegression(C=0.1, L2) 모델
  → 딜 승산 점수(0~100) 산출
```

## 3. 정제·가공·분할 절차 및 후속 활용

### 3.1 학습 / 검증 분할 (딜 승산 점수 모델)

- **분할 기준**: 행 단위 무작위 분할 대신, 10개 입력 특성 조합이 같은 행을 하나의 그룹으로 지정
- **분할 방식**: `StratifiedGroupKFold` 5-Fold × 시드 변경 10회 반복 = 총 50개 평가 fold
- **분할 이유**: 동일한 특성 조합이 학습·평가 데이터에 함께 들어가면 모델이 같은 입력을 미리 학습해 성능이 부풀려지는 것을 방지

| 필드 | 처리 |
| --- | --- |
| `Status` | 목표값(`Won`=1/`Lost`=0)으로 분리, 입력 특성에서 제외해 데이터 누수 방지 |
| `Product`, `Seller` | Salvirt 내부 익명 코드로 SalesLuv와 매핑 불가 · 담당자 편향 우려로 제외 |
| `Comp_size`, `Partnership`, `Growth` 등 10개 | 단일 미팅에서 일관되게 추출하기 어려워 1차 모델에서 제외 |
| 선택된 10개 특성 | One-Hot Encoding 후 그룹 기준으로 사용 |

### 3.2 후속 단계 활용 적합성 및 재현성 관리

| 구분 | 항목 | 기준 / 결과 | 설명 |
| --- | --- | --- | --- |
| 모델 검증 | 지표 | ROC-AUC 0.793 · Brier Score 0.190 · Accuracy 71.0% | 검증 기준일 2026-08-17, `StratifiedGroupKFold` 50 fold 평균 |
| 모델 비교 | 대안 | CatBoost(ROC-AUC 0.792), MLP(0.785) | Logistic Regression과 성능 차이가 거의 없거나 낮아 최종 채택하지 않음 |
| 최종 모델 | 선정 | `OneHotEncoder(handle_unknown="ignore") + LogisticRegression(C=0.1, L2)` | 데이터 규모(365건)에 적합, 해석 용이, 추가 인프라 불필요 |
| 후속 활용 | 서비스 반영 | 미팅 분석 Agent → 10개 특성 추출 → ML 모델 → 딜 승산 점수 표시 | `agent_run.output_snapshot`에 `features`, `score`, `model_version` 보존, 화면에는 참고 정보로만 노출 |
| 재현성 | 재학습 기준 | `pipeline_stage.outcome_code=confirmed`+`contract_signed_on` → Won, `=cancelled`+`closed_on` → Lost | 점수 계산 시점 이전 특성과 이후 결과만 학습 표본으로 사용, 결과 이후 정보 유입 차단 |
| 비식별화 | 구조 보존 | 원본 대비 시트 수·순서·병합·서식·수식 오류 없음 | XLSX/DOCX 자동 검증 통과 시에만 최종본으로 저장 |
| 비식별화 | 개인정보 제거 | 주민등록번호·계좌번호·서명 이미지 등 삭제 | `data-sanitization-rules.md` 값별 처리 기준 적용 |

## 4. 한계 및 향후 계획

- 딜 승산 점수 학습 데이터는 365건으로 규모가 작고, 동일 특성 조합에서도 실제 결과(`Won`/`Lost`)가 갈리는 사례가 있어 현재 점수는 참고용으로만 사용한다.
- 학습 데이터는 SalesLuv의 실제 한국어 영업 미팅이 아닌 외부 B2B 데이터이므로, 서비스 실제 종료 딜이 쌓이면 3.2절 기준으로 재학습이 필요하다.
- 비식별화 트랙은 원본-가상 대응표를 남기지 않는 정책상, 이번 초안에는 항목별 변경 건수를 수치로 포함하지 않았다. 필요하면 자동 검증 스크립트 실행 로그를 별도로 남기는 방식을 검토한다.
- 표 비식별화 자료(`data/sample/`)의 정확한 수집 출처·건수·라이선스는 `docs/데이터 수집 보고서.md`에서 `확인 필요`로 남아 있어 함께 확정이 필요하다.
